# Getting the first replay to match

Notes from 2026-09-26, using game v0.111.0 (`41cef1ea`), sts2-cli `084d1aa`, and
.NET 9.0.2 on Apple Silicon. Current usage is in [Running fights from Python](combat-parity.md).

I started with the last fight of a Defect A10 run: the Insatiable, lost on turn 6.
The game had saved an `.mcr`; Spirebird had recorded the same fight. That gave me inputs
and checkpoints to compare while getting the headless worker running.

## The recordings

The `.mcr` contains the starting run state, 34 events, and 49 checkpoints. The game's
`PacketReader.Read<CombatReplay>` reads it once the model and net-type registries are initialised.
Of those events, 27 are player inputs; the rest are turn transitions and an action resume.

Spirebird records the same checkpoints through `ChecksumTracker.ChecksumGenerated`, plus
turn boundaries and the final player HP. It doesn't record the resume event, so I used the
`.mcr` to drive replay. [`spgn.py`](../sts2bridge/spgn.py) reads the Spirebird framing and CBOR.

The `.mcr` anonymises player IDs. Compare against the re-hashed stored state, as the game's
replay checker does, rather than the original live hash beside it.

## What needed fixing

The Godot stubs and bootstrap from sts2-cli got the game loaded. Three things stood between
that and a matching replay:

- **Runtime.** `RollForward=LatestMajor` selected .NET 10, where this version of Harmony
  failed to install its patches. Pinning .NET 9 fixed that.
- **Registries.** `MessageTypes.Initialize()` and `ActionTypes.Initialize()` were needed
  to decode recorded actions.
- **Checkpoints.** TestMode disables the tracker and skips the action-finished subscription.
  I re-enabled it and attached the post-action checksum callback to `GameAction.JustBeforeFinished`.

The first replay matched 1/49 checkpoints. Restoring the callbacks got it to 29/49;
the remaining 20 hashes matched, but their context strings included per-process card instance
numbers. Normalising those numbers gave 49/49. The final state was player HP 0, boss HP 90.
Six runs produced the same hash sequence; dropping an input diverged at the next checkpoint.

The worker waits for the action queue to settle, including choices and turn transitions.
An energy change or a new turn number can happen before a card has finished resolving.

## What the checksums cover

`NetFullCombatState` includes creature HP, block and powers; player resources, ordered card
piles, potions, relics and orbs; run RNG and combat-relevant player RNG; and choice/reward IDs.
It leaves out monster move state and intents, card fields outside `SerializableCard`, and
player Rewards/Shops RNG. The final checkpoint precedes death; Spirebird's end record gives
the terminal player HP.

This fixture has one enemy, no potions, and no hook actions. The current tests add encounter
sweeps and run handling, but this remains the recorded case used for checksum comparisons.

## Why the bridge has its own action handling

At `084d1aa`, sts2-cli's command layer takes several shortcuts: direct end-turn calls,
a global card selector that skips choice-ID reservation, custom rewards and between-act
healing, and reloads through `EnterAct`. Those are different paths from the recorded game inputs.
I kept its hosting code and used the game's action queue for the bridge.

One inherited shortcut remains: the `Neutralize.OnPlay` replacement applies damage and Weak
directly, bypassing attack hooks. The reference fight doesn't use that card.

I also looked at zhiyue/sts2-rl-agent `1b7e7ce`. Its queued card-play path was useful, but the
bridge needed API updates for v0.111.0. Its end-turn, potion, choice, and AutoSlay paths differed
from manual play, and its step detection could return before an action finished. I didn't run it.

The next step was exposing the same replay path one input at a time. That's now
[`CombatWorker.step`](combat-parity.md#step-a-combat), and it matches the same 49 checkpoints.
